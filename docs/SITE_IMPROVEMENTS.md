# HANDOFF: トピカ サイト改善プロジェクト（ドメイン移行 + SEO + UX）

作成日: 2026-07-13 / 作成: Claude Chat（戦略セッション）
対象リポジトリ: sotar0826/topica（Astro + Cloudflare Pages）

## 背景と目的

記事拡充と並行して、アクセス数と満足度を高めるための基盤改善を行う。
Chat側での検討の結果、以下を実装対象とする（フィードバックボタンは対象外と決定済み）。

- サイト名は「トピカ」のまま変更しない
- ドメインはXServerドメインで新規取得（初回0円キャンペーン利用、支払い発生は1年後の更新から）
- ドメイン移行を最初に行う（OGP・sitemap・canonical等がすべて最終ドメインに依存するため）

## Phase 0: 人間側タスク（Sotaroが手動で実施）

Claude Codeの作業対象外。Phase 1着手前に完了させること。

1. ドメイン名の決定と空き確認（サイト名は「トピカ」のままなので topica.jp / topica-law.com など。J-PlatPatでの商標確認も推奨）
2. XServerドメインで新規取得（初回利用0円キャンペーン対象か確認。対象TLD: .com / .net / .jp 等）
3. XServerドメイン管理画面でネームサーバーをCloudflareに変更（Cloudflareダッシュボードに新ドメインをサイト追加 → 表示される2つのNSをXServer側に設定）
4. Cloudflareダッシュボード → Workers & Pages → topicaプロジェクト → Custom Domains に新ドメインを追加（SSL自動発行を確認）
5. Phase 1完了・デプロイ後: Search Consoleに新ドメインのドメインプロパティを追加（DNS認証。CloudflareのDNSにTXTレコード追加）→ 旧プロパティ（topica.pages.dev）から「アドレス変更」ツールで移転通知 → 新プロパティにsitemap再送信
6. GA4の管理画面でデータストリームのURLを新ドメインに更新

## Phase 1: ドメイン移行（コード側）

**目的**: 全URLを新ドメインに切り替え、pages.devへのアクセスを301で新ドメインへ転送する。

- `astro.config.mjs` の `site` を新ドメインに変更（canonical / sitemap / OGP url / JSON-LD が site 参照で一括切替になっているか確認。ハードコードされた `topica.pages.dev` をリポジトリ全体でgrepして排除）
- Pages Functions でホスト名ベースの301リダイレクトを実装（`functions/_middleware.js`）:
  - `request.url` のホスト名が **正確に** `topica.pages.dev` の場合のみ、パス・クエリを維持して新ドメインへ301
  - **注意**: プレビューデプロイ（`<hash>.topica.pages.dev`）はリダイレクトしないこと。完全一致で判定する
- `robots.txt` のsitemap URLを新ドメインに更新
- 受け入れ条件:
  - `curl -I https://topica.pages.dev/minpo/sakugo/` が `301` + `Location: https://<新ドメイン>/minpo/sakugo/` を返す
  - 新ドメインの任意ページで canonical / og:url / sitemap がすべて新ドメインを指す
  - プレビューデプロイが従来どおり閲覧できる

## Phase 2: titleタグ最適化

**目的**: 検索意図キーワードを含むtitleでCTR・順位を改善する。

- 記事frontmatterに `seoTitle` フィールドを追加（未指定時は現行の `{title}｜トピカ` にフォールバック）
- 基礎編の推奨パターン: `{トピック}とは？{条数等}の要件をわかりやすく解説｜トピカ`（例: 「錯誤とは？民法95条の要件をわかりやすく解説｜トピカ」）
- 応用編: `{トピック}の判例・学説と論述のポイント｜トピカ` 系
- 用語集・コラム・科目トップにも同方針を適用
- 全角30〜35字程度に収める（検索結果での省略を避ける）
- meta description は既に良質なので原則変更不要。titleとの重複が激しいページのみ調整
- 全記事分の `seoTitle` は機械的に生成してよいが、**主要キーワード（〜とは/わかりやすく/条数）が自然に入っているか記事ごとに確認**すること
- 受け入れ条件: 全ページの `<title>` がパターン準拠、og:title / twitter:title も追随

## Phase 3: OGP画像の自動生成

**目的**: 全ページ共通の `ogp-default.png` をやめ、記事タイトル入りOGPを自動生成する。

- 推奨構成: satori + @resvg/resvg-js を使い、Astroのエンドポイント（`src/pages/og/[...slug].png.ts`）でビルド時に静的生成
- フォント: Noto Sans JP（サブセット化してリポジトリに同梱。ビルド時のネットワーク取得は避ける）
- デザイン: サイトロゴ + 科目名（民法等）+ 記事タイトル + 基礎編/応用編バッジ。1200x630
- 各ページの `og:image` / `twitter:image` を生成URLに差し替え。トップ・科目トップは専用デザインでも既存defaultでも可
- Cloudflare Pagesのビルド環境で resvg のネイティブバイナリが動くことを最初に検証すること（動かない場合は astro-og-canvas に切替）
- 受け入れ条件: 任意記事のOGP URLをブラウザで開くとタイトル入り画像が表示される。X/LINEのカードバリデータで確認

## Phase 4: 用語集の1用語1ページ化

**目的**: 「〜とは」系ロングテール検索の受け皿を作る。

**完了（2026-08-26）**: 20用語すべてを本文1,200字以上・見出し3個以上へ再編集し、DefinedTerm、canonical、関連記事、Pagefind本文指定、AdSense、サイトマップ収録を品質ゲートとビルド監査で一元管理した。定義だけの短いページは検索公開しない設計に変更済み。

- 現行 `/yougo/` はインデックスとして維持し、`/yougo/{term-slug}/` を新設
- 用語データをコンテンツコレクション化（term, reading, definition, 関連条文, 関連トピックslug[]）
- 各用語ページ: 定義（現行の用語集より一段詳しく、2〜4段落）+ 関連トピックへのリンク + 関連用語
- title: `{用語}とは？意味をわかりやすく解説｜トピカ`
- DefinedTerm系のJSON-LDを付与
- 既存記事本文から用語ページへの内部リンクはPhase 9のツールチップと統合するため、この段階では無理に張らなくてよい
- 受け入れ条件: 全用語が個別URLを持ち、sitemapに含まれ、インデックスから遷移できる

## Phase 5: 判例インデックス・判例個別ページ

**目的**: 「最判平○.○.○」「{論点} 判例」検索からの流入源を作る。

- `/hanrei/` インデックス + `/hanrei/{slug}/` 個別ページを新設
- frontmatter: 裁判所・判決日・出典（民集○巻○号等）・事件名（通称）・関連トピックslug[]・関連条文
- 本文構成: 事案の概要 / 判旨 / 意義・位置づけ / 関連トピックへのリンク（既存の応用編・コラムの記述と重複させず、相互リンクで補完する）
- 初期対象: 既存記事・コラムで言及済みの主要判例から20〜30件を抽出して作成（ARTICLE_GUIDE.mdの文体基準に従う）
- title: `{事件通称 or 最判平○.○.○}｜{論点}の判例解説｜トピカ`
- 受け入れ条件: インデックスが判決日・科目で整理されており、既存記事から該当判例ページへ最低1本ずつリンクがある

## Phase 6: サイト内検索（Pagefind）

- ビルドコマンドを `astro build && pagefind --site dist` に変更（package.jsonとPagesのビルド設定両方）
- ヘッダーに検索UI（Pagefind標準UI、モーダルまたは検索ページ `/search/`）
- 日本語検索の精度を確認（`html` の `lang="ja"` が付いていること）
- インデックス対象を記事本文に限定（ヘッダー・フッター・ナビは `data-pagefind-ignore`）
- 受け入れ条件: 「錯誤」「表見代理」等で該当記事が上位に出る。モバイルで検索UIが使える

## Phase 7: 学習進捗トラッキング

- localStorageベース、ログイン不要。キー設計例: `topica:read:{slug}` = ISO日付
- 記事末尾に「読了にする」ボタン（トグル）
- 科目トップの各トピック行に読了チェックマーク表示 + 科目ごとの進捗バー（例: 民法 32/51）
- トップページに全科目の進捗サマリー（未読了ユーザーには非表示）
- リセット機能（科目単位 or 全体）を目立たない位置に
- 実装はAstroアイランド（バニラJSまたは軽量コンポーネント）。SSR/静的生成と干渉しないようクライアントサイドで描画
- 受け入れ条件: 読了 → 科目トップに反映 → リロード後も保持 → リセットで消える

## Phase 8: ○×クイズのインタラクティブ化 + 横断一問一答

- 記事内の確認問題を「タップで答えを開く」形式に変更（`<details>` ベースで可。開いた時に正誤の自己申告ボタンを置くとPhase 7の進捗と将来連携できるが、初期実装では不要）
- クイズデータを本文べた書きからコンテンツコレクション or frontmatter配列に構造化（question, answer: boolean, explanation, 関連トピックslug）。既存73記事分の移行はスクリプトで機械的に抽出 → 目視確認
- `/quiz/` ページ新設: 全科目 or 科目指定でランダム10問出題 → 即時正誤表示 → 結果画面に間違えた問題の関連トピックリンク
- 短答式（記述）問題はランダム出題の対象外とし、記事内のみに残す
- 受け入れ条件: 記事内クイズがタップ開閉で動作、/quiz/ でランダム出題〜結果表示まで完走できる

## Phase 9: 追従目次・ダークモード・用語ツールチップ

- **追従目次**: 応用編など長い記事にデスクトップはサイドバー追従、モバイルは開閉式の目次。h2/h3から自動生成
- **ダークモード**: CSS変数化 → `prefers-color-scheme` 追従 + 手動トグル（localStorageに保存）。図表コンポーネント（今後の4パターン図解含む）もCSS変数を使う前提で設計
- **用語ツールチップ**: `<Term slug="...">対抗要件</Term>` のようなコンポーネントで、タップ/ホバーで用語集の短い定義をポップオーバー表示 + 用語ページ（Phase 4）へのリンク。既存記事への適用は新規記事・リライト時に順次でよい
