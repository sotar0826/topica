## 1. 記事作成・拡充ワークフロー

### 1.1 4段階制ワークフロー

記事の質を担保しつつセッションをまたいで継続できるよう、次の4フェーズに分ける。  
各フェーズの完了状態を `docs/CONTENT_PLAN.md`（別途作成）で追跡する。

---

#### Phase 1 — 項目分け（Scope Planning）

**目的**: 「次に何を書くか」を決める。

**担当ツール**: Code セッション

**インプット**
- `HANDOFF.md` の進捗表（現状の完成トピック一覧）
- `src/data/curriculum.ts`（全トピック定義）

**作業内容**
1. `curriculum.ts` の全トピックと `HANDOFF.md` の進捗を突き合わせ、未着手・応用編未作成・コラム候補を列挙する
2. 各候補に**優先度タグ**を付ける（基準：試験頻出度・既存記事との依存関係・ユーザーの学習フロー上の空白）
3. 結果を `docs/CONTENT_PLAN.md` に記録する（スラッグ / タイトル / 種別 / 優先度 / 理由 の表形式）

**完了の定義**: 今後2〜3セッション分の書き候補リストが優先度付きで揃っている状態

---

#### Phase 2 — 各項目で何を書くか（Outline Planning）

**目的**: 執筆前に「どの判例を使うか」「要件効果をどう構造化するか」を確定させ、事実誤認や判例捏造を防ぐ。

**担当ツール**: Cowork（外部情報源の調査）＋ Code セッション（既存記事との整合確認）

**作業内容**
1. **条文確認**（Cowork）: e-Gov法令検索で対象条文の現行文言を取得し、構成メモに正確な条文番号・文言を記録する
2. **判例確認**（Cowork）: 裁判所ウェブサイトで使用予定の判例を検索し、事件番号・日付・判示事項の要旨を確認する。原文に確信が持てない場合は「判例引用不可・要旨のみ」と明記
3. **構成メモ作成**（Code）: 下記のスタブ形式で `src/content/<科目>/<slug>.md` を作成する

```markdown
---
title: "（タイトル）"
description: ""
level: "basic"   # or "advanced"
related: []
---

<!-- OUTLINE MEMO（執筆前の構成メモ。執筆時に削除） -->
<!-- 扱う条文: 民法○条 -->
<!-- 使用判例: 最判○年○月○日（確認済み／要旨のみ）-->
<!-- 要件: ①… ②… -->
<!-- 効果: … -->
<!-- つまずき箇所: … -->
<!-- 試験頻出度: 高／中 -->
```

**完了の定義**: スタブファイルが作成され、判例・条文が確認済みの状態

---

#### Phase 3 — 執筆（Writing）

**目的**: スタブを完成記事に育てる。

**担当ツール**: Code セッション

**作業内容**
1. `CLAUDE.md` の執筆方針を確認してから書き始める
2. 1セッションで完成させる分量の目安：基礎編 1〜2本 または 応用編 1本
3. 執筆後、英単語混入チェックを走らせる（HANDOFF.md §4 参照）

```powershell
# 英単語混入チェック例（完成ファイルに対して実行）
grep -Pn "\b(too|debtor|contract|creditor|property|claim|right|court|judge)\b" src/content/minpo/*.md
```

4. `curriculum.ts` への追加が必要な新トピックの場合は忘れず更新する

**完了の定義**: ファイルが完成し、`npm run dev` で表示が崩れていない状態

---

#### Phase 4 — レビュー（Review）

**目的**: 品質と方針準拠を確認してからデプロイする。

**担当ツール**: Code セッション（`/code-review` スキル活用も可）

**チェックリスト**

| チェック項目 | 確認方法 |
|---|---|
| 文体（口語に逃げていないか） | 目視 |
| 端的な要約がトピック冒頭・難所の節末にあるか | 目視 |
| 要件・効果が `### 要件` / `### 効果` で構造化されているか | 目視（第2編以降の制度トピックのみ） |
| コールアウト（⚠️ / 🎯）が1ページ2〜3個以内か | 目視 |
| 判例形式「最判○年○月○日」が正しいか | 目視 |
| 全角約物の隣接強調が崩れていないか | dev サーバーで目視 |
| 英単語混入がないか | grep |
| `related:` の slug が実在するか | `getCollection` ビルドエラーで気づける |
| 前後リンクが正しく動いているか | dev サーバーで動作確認 |

**完了の定義**: チェックリストを通過し、本番デプロイ準備ができている状態

### 1.2 外部情報源の活用方針

#### ▼ 絶対原則（交渉の余地のない大前提）

> **条文・判例を間違えること、架空の条文・判例を挙げることは絶対にあってはならない。**
>
> - 条文は必ず e-Gov 法令検索で現行文言を確認してから記述する。記憶での記述は禁止。
> - 判例は事件番号・判決日・法廷を裁判所ウェブサイトで確認できたもののみ引用する。確信が持てない場合は「要旨」と明記し、創作・断定をしない。確認できないものは「判例の内容は確認できないため省略」と明記するか省く。
> - この原則はコンテンツの質・量・締め切りよりも優先される。

---

#### 優先度 1 — 一次資料（絶対条件）

条文・判例の記述はここで確認してから書く。これ以外を根拠にしない。

| 情報源 | URL | 用途 | Cowork での使い方 |
|---|---|---|---|
| e-Gov 法令検索 | https://elaws.e-gov.go.jp/ | 条文の現行文言・条番号の確認 | `WebFetch` で対象条文ページを直接取得 |
| 裁判所ウェブサイト 判例検索 | https://www.courts.go.jp/app/hanrei_jp/search1 | 判決全文・事件番号・判決日・法廷の確認 | `WebSearch` で件名検索 → `WebFetch` で詳細ページ取得 |
| 法務省 法制審議会・改正関連 | https://www.moj.go.jp/ | 改正立法の趣旨・パブコメ・立案経緯 | `WebFetch` で該当ページ取得 |

引用形式の原則：
- 条文 → 「民法○条○項」（改正後の現行文言に即して引用）
- 判例 → 「最判平成○年○月○日民集○巻○号○頁」（事件番号まで確認できた場合は追記）

---

#### 優先度 2 — 学術資料（学説・解釈論の充実に使う）

条文に直接書かれていない学説・解釈論の紹介に用いる。論文は要旨での参照でも可。

| 情報源 | URL | 用途 | 注意点 |
|---|---|---|---|
| CiNii Research | https://cir.nii.ac.jp/ | 法律学術論文・紀要の検索 | 本文は機関リポジトリへのリンクで無料公開されているものも多い |
| J-STAGE | https://www.jstage.jst.go.jp/ | 査読論文の検索・閲覧 | 要旨のみ参照も可。本文有料の場合は要旨で代替 |
| 大学機関リポジトリ（IRDB 等） | https://irdb.nii.ac.jp/ | 各大学の紀要論文（多くが無料公開） | CiNii Research 経由で到達することが多い |

---

#### 優先度 3 — 実名の専門家解説（補強用）

一次資料・学術資料で補えない実務的な解説に限り参照する。出典として引用しない（あくまで参考）。

対象となるもの：
- 執筆者名・所属・登録番号が明記された弁護士・法律事務所の解説記事
- 日本弁護士連合会（日弁連）の公式解説・意見書
- 省庁の Q&A・解説パンフレット（改正法の実務的説明など）

使い方：「この解釈は実務上このように扱われている」という文脈の確認に使う。記事内での引用元としては掲載しない。

---

#### 避けるべき情報源

以下は参照しない。記事の根拠として使わない。

| 種別 | 例 | 理由 |
|---|---|---|
| 著者不明のまとめサイト | 法律系まとめ、法律 Wiki 類 | 誤情報・古い情報の混入リスクが高い |
| SEO 量産記事 | 「わかりやすく解説」系の法律メディア | 法的正確性より読まれやすさを優先した記事が多い |
| Q&A サイト | Yahoo!知恵袋、教えて!goo 等 | 回答者の専門性が担保されない |
| 予備校テキスト・ブログ | 伊藤塾・LECのブログ等 | 学説の整理は参考にできるが、出典の独自確認が必要 |

---

#### クオリティの差別化ポイント：学説・解釈論の充実

> 条文と判例の正確な記述は「最低限の土台」であり、差別化の余地はない。  
> **記事の深みを決めるのは、条文に直接書かれていない「学説・解釈論」をどれだけ充実させられるか**、である。

学説を紹介する際のルール：

- 立場を必ず明示する：**通説**・**有力説**・**少数説**・**判例の立場**の区別を明確にする
- 対立の構図を示す：「A 説は〜と解する。これに対し B 説は〜と批判する。判例は〜の立場をとる」のように論点の軸を示す
- 出典を意識する：学術論文・教科書的に確立された整理（内田民法・我妻民法講義等）を念頭に置き、「通説とされている」根拠を自分で確認してから書く
- 試験との接続を明示する：論文試験で問われやすい対立がある場合は「🎯 **試験で狙われる**」のコールアウトと合わせて、どちらの立場で答案を書くべきかの方向性を示す

## 3. サイト構成・UI改善

### 3.1 現状の課題整理

コードレビューから把握している現状の制約：

| 課題 | 詳細 |
|---|---|
| 記事内目次がない | 長い記事（応用編など）で節の全体像がつかめない |
| サイト内検索がない | 特定トピックを探すには一覧ページを頼るしかない |
| 一覧ページの情報量が少ない | トピック名だけで、難易度・完成状態・説明文がない |
| OGP 画像が設定されていない | SNS シェア時にカード表示が出ない |
| 印刷スタイルがない | 学習素材なので印刷需要がある可能性 |
| モバイルでのナビ | ヘッダーの 3 リンクが画面幅によっては窮屈になりうる |

### 3.2 改善案

#### A. 記事内目次（Table of Contents）

- **実装方法案**: Astro の remark プラグイン（`remark-toc` または `rehype-autolink-headings` + 目次コンポーネント）で `h2`/`h3` から自動生成
- **表示位置案**: 記事本文の冒頭（`<article>` の前）に折りたたみ式で配置。デスクトップではサイドバー固定も検討
- **優先度**: 高（長文記事が多いため効果が大きい）

#### B. 静的全文検索（Pagefind）

- **ツール**: [Pagefind](https://pagefind.app/) — ビルド後のHTMLをインデックス化する静的検索。Astro との相性が良く、追加バンドルサイズ極小
- **実装手順案**: `npm run build` 後に `npx pagefind --site dist` を走らせてインデックス生成 → ビルドスクリプトに組み込み → 検索UIコンポーネントをヘッダーに配置
- **優先度**: 中（コンテンツ量が増えるほど価値が高まる）

#### C. 一覧ページの強化

- **追加情報案**: 各トピックカードに短い説明文（frontmatter の `description` を流用）と「応用編あり」バッジを表示
- **既読マーク**: `localStorage` で訪問済みトピックを記録し、一覧でチェックマークを付ける（サーバー不要・プライバシー安全）
- **優先度**: 中

#### D. OGP・SNS メタタグ

- **追加するタグ**: `og:title` / `og:description` / `og:image` / `og:type` / `twitter:card`
- **og:image の方針**: 汎用の静的画像（`public/og-default.png`）を先に作成し、全ページに適用。余裕があれば科目別・トピック別に分ける
- **実装場所**: `BaseLayout.astro` の `<head>` に追記
- **優先度**: 高（SEO とも連動）

#### E. 印刷スタイル

- **実装**: `global.css` に `@media print { ... }` を追加。ナビゲーション・ヘッダー・フッター・AI テンプレートセクションを非表示に
- **優先度**: 低

#### F. モバイルナビ改善

- **課題の確認が先**: dev サーバーをモバイル幅（375px）でチェックし、本当に崩れているか確認する
- **改善案（崩れていた場合）**: ハンバーガーメニューへの変更、またはナビリンクを縦積みに
- **優先度**: 要確認後判断

## 4. SEO対策・広告導入

### 4.1 SEO

#### 現状の強み

- 静的サイト（Cloudflare CDN）= Core Web Vitals は有利
- URL 構造がクリーン（`/minpo/sagi-kyohaku/`）
- `title` / `description` は全ページ設定済み
- `noindex` が管理ページに設定済み

#### 着手すべき対応（優先度順）

| 対応 | 詳細 | 工数 |
|---|---|---|
| **sitemap.xml 生成** | `@astrojs/sitemap` プラグインを `astro.config.mjs` に追加。`site` プロパティの設定確認（現状 `topica.pages.dev`） | 小 |
| **OGP タグ追加** | 上記 §3.2-D と同一作業。同時に対応 | 小 |
| **JSON-LD 構造化データ** | `schema.org/Article` または `LearningResource` 型で各トピックページに追加。Astro コンポーネントで一括実装可 | 中 |
| **Google Search Console 登録** | サイトマップ送信。現状登録済みかどうか確認が必要 | 小（手動） |
| **内部リンク強化** | 記事内で関連トピックへのテキストリンクを増やす。現状は `related:` による「先に読む」ボックスのみ | 中（執筆作業と並行） |
| **Bing Webmaster Tools 登録** | Google 登録後に対応 | 小（手動） |

#### やらないこと（判断済み）

- **AMP**: 静的サイトで既に高速。AMP の制約を受け入れるメリットがない
- **キーワード詰め込み**: 法律用語が自然に含まれるので人工的な最適化は不要

### 4.2 広告導入

#### 現状

`BaseLayout.astro` に `<div class="ad-slot"></div>` が既にある（将来用プレースホルダー）。

#### 方針

**Google AdSense を第一候補とする。**

| 確認事項 | 状況 |
|---|---|
| コンテンツ量 | 公開ページ 100+ 本 → AdSense 審査の実績要件は十分 |
| コンテンツの種類 | 法律教育 → ポリシー上問題なし |
| 収益規模の期待値 | 法律・司法試験カテゴリは CPC が高い傾向（参考値：¥30〜¥200/クリック）。ただしトラフィック次第 |

#### 導入ステップ（計画レベル）

## 5. Claude 運用改善

### 5.1 現状の課題

`HANDOFF.md` は**安定した参照ドキュメント**として機能しているが、次の問題がある：

- セッションをまたぐと「前回どこまでやったか」が不明確になる
- 複数の Code セッションと Cowork セッションが混在すると、決定事項が会話の流れの中に埋もれる
- HANDOFF.md を毎回更新すると内容が煩雑になり、安定した参照ドキュメントとしての価値が下がる

### 5.2 2ファイル体制の設計

| ファイル | 役割 | 更新頻度 |
|---|---|---|
| `HANDOFF.md` | **安定参照**: 環境・アーキテクチャ・執筆方針の確定済み仕様 | 環境変更・仕様変更時のみ |
| `docs/SESSION_NOTES.md` | **ローリングログ**: 直近の進捗・決定事項・引き継ぎ事項 | セッション終了時に毎回更新 |

### 5.3 SESSION_NOTES.md のフォーマット仕様

```markdown
# セッションノート

## オープン事項（未解決・判断待ち）

（内容があれば箇条書きで記載。解決したら削除）

---

## 直近セッションログ

### YYYY-MM-DD [Code / Cowork / 両方]

**フォーカス**: （このセッションで取り組んだテーマ）

**完了**:
- （完了したタスク。デプロイ済みなら「デプロイ済み」と明記）

**未完了・持ち越し**:
- （着手したが終わらなかった作業）

**決定事項**:
- （このセッションで確定した方針・設計。後から覆さないもの）

**次セッションで最初にやること**:
- （次のセッション開始直後に実行すること。1〜3項目）

---

（前のセッションのエントリがここに積み重なる。古くなったら削除）
```

### 5.4 運用ルール

#### セッション開始時（毎回必須）

1. `docs/SESSION_NOTES.md` を読む → 直近ログと「次セッションで最初にやること」を把握する
2. `HANDOFF.md` の §2（環境・運用）を確認する（特に Node.js PATH と deploy コマンド）
3. 作業前に「今日のフォーカス」をユーザーに確認し、SESSION_NOTES の「次セッション」との乖離があれば擦り合わせる

#### セッション終了時（毎回必須）

1. `docs/SESSION_NOTES.md` に今日のエントリを**冒頭のセッションログセクションに追記**する
2. 「オープン事項」を更新する（解決済みは削除、新規発生は追加）
3. 完了したトピックがあれば `HANDOFF.md` §5「現在の進捗」も更新する
4. デプロイした場合は SESSION_NOTES の「完了」欄に「本番デプロイ済み」と明記する

#### Cowork セッション固有のルール

- Cowork セッションでは SESSION_NOTES の更新ができない場合がある（ファイル書き込みの有無による）
- その場合、**Cowork の調査結果をスタブファイルのコメントに埋め込んでおき**、後続の Code セッションで SESSION_NOTES を更新する
